# T-CAMS — Dashboard TSCC

React + TypeScript + Vite application backed by Supabase Auth, Postgres, and private Storage. Hosting is configured for Vercel. The interface preserves the original T-CAMS visual system and case workflows.

## Local development

Use Node.js 22.12+ (Node 24 is used in CI).

```sh
npm ci
cp .env.example .env.local
# Set VITE_SUPABASE_PUBLISHABLE_KEY in .env.local
npm run dev
```

Before a lockfile exists on a fresh initialization, use `npm install`; CI persists the generated lockfile after successful verification. Subsequent installs use `npm ci`.

```sh
npm test
npm run typecheck
npm run build
npx playwright install chromium
npm run test:e2e
```

## Supabase

Project: `eosjflarlcwygtcsvaio` in Singapore.

The applied SQL migrations are in `supabase/migrations`. `supabase/schema.sql` is a reference snapshot of the initial schema, not an additional migration. Apply migrations once using the Supabase CLI or SQL editor. Every business table has row-level security enabled. Business tables are unavailable to anonymous clients.

Frontend configuration uses only:

- `VITE_SUPABASE_URL`
- `VITE_SUPABASE_PUBLISHABLE_KEY`

Privileged keys must never appear in `VITE_*` variables, source files, or Vercel frontend configuration.

### Account setup

Invite users through **Supabase Dashboard → Authentication → Users → Add user → Send invitation**. Configure the invitation URL to point to the deployed app with `?setup=1` so the invitee sets their password.

New users receive the `Requester` role. Bootstrap the first administrator once using the SQL editor:

```sql
update public.profiles
set role = 'Admin'
where email = 'YOUR_ADMIN_EMAIL';
```

Administrators can manage roles, units, regions, and employee IDs on the Configuration page. Application authorization uses the protected profile role in Postgres and never relies on editable user metadata. Requesters must be explicitly linked to their cases by a team leader or administrator; matching a person's name does not grant access.

| Role | Access |
| --- | --- |
| TSCC User | Assigned, collaborating, and self-created cases; drafts; personal reporting; case updates |
| Team Leader | All cases, assignments, monitoring, reports, workload, and case updates |
| Department Head | Published cases, reporting drilldowns, workload, and investigation signals; read-only case access |
| Admin | Configuration, account access, all cases, and staff-assignment management |
| Requester | Own linked, submitted tickets; requester-visible comments and activity; permitted attachments |

Internal notes and legacy source snapshots are stored separately from requester-visible case data. Audit records are generated by a database trigger, and users cannot insert or edit the audit trail through the API. Case attachments and avatars are in private buckets, with short-lived signed download URLs.

### Legacy case import

The original HTML contains 5,068 business records. Source HTML and extracted records are excluded from Git and deployment assets. The import keeps each source record in protected `case_internal.legacy_source` and preserves original ticket numbers, timestamps, handling durations, source categories, and descriptions.

To import into a different project, set a server-only `SUPABASE_SECRET_KEY` (or legacy `SUPABASE_SERVICE_ROLE_KEY`) in your terminal environment and run:

```sh
npm run import:legacy -- /absolute/path/tcams_production_v21_department_head_drilldown.html
```

The importer is idempotent and preserves existing case edits. Naive timestamps in the source are interpreted in Asia/Jakarta. Imported PIC names are normalized, while unknown names are retained. After inviting staff, use **Configuration → Link Imported PIC Assignments** to connect primary PIC identities to accounts. Collaborators and requester account links can be assigned on the case detail page. No source passwords or simulated accounts are migrated.

## Vercel deployment

Import `TBIMPCS/Dashboard-TSCC` into Vercel. Select **Vite**, repository root `.`, build command `npm run build`, and output `dist`. Add the two frontend environment variables to Production and Preview. `vercel.json` configures client-side route fallback and response headers. Git integration automatically creates production deployments from `main` and preview deployments for other branches.

In **Supabase → Authentication → URL Configuration**, set the Site URL to the Vercel production origin and add:

- `https://YOUR_PRODUCTION_DOMAIN/**`
- `http://localhost:5173/**` for local development
- Explicit preview origins when preview authentication is needed

Do not permit every `*.vercel.app` origin. Restrict previews to this project's URLs.

Invitation and password-reset links use `/account?setup=1`. Passwords are managed by Supabase and are never saved as plaintext by the application.

## Application structure

`src/components` contains tables, charts, calendar, filters, and common UI. `src/pages` contains the case, reporting, account, and administration workflows. `src/hooks` provides authentication and server data. `src/lib` contains types, Supabase configuration, and shared reporting calculations. Heavy pages and charts are loaded through route-level lazy imports.

Reports and their drilldowns use the same filtered dataset. All authorized records are loaded using paginated Supabase requests, so reports are not silently limited to the API's 1,000-row response limit. Table display is paginated separately. Data refresh is available from the header.

The former AI insight simulation is represented by evidence-based investigation signals; no external LLM service is configured. Quick Draft structures pasted notes using their first line as a subject and keeps the full text as the description. CSV exports include formula-injection protection.

English and Bahasa Indonesia navigation preferences are persisted per user. The case content remains in its original language.

## Verification

CI runs analytic/access unit tests, TypeScript checks, the production build, and Playwright tests for login failure, draft-to-submitted-to-closed workflow, comments, manager drilldowns, requester UI isolation, mobile navigation, and calendar persistence. Browser tests use synthetic API fixtures, not production records. Database authorization is verified separately using transactional Supabase RLS checks.
